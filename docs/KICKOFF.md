## 0. 이 문서를 읽는 법 (Claude Code에게)

이 문서는 이 프로젝트의 **단일 진실 원천(single source of truth)** 이다. 구현 중 이 문서와 충돌하는 판단이 필요하면 임의로 결정하지 말고 재성에게 질문한다.

- §1~2는 **왜**를 정의한다. 모든 구현 판단의 기준이므로 반드시 먼저 읽는다.
- §3~5는 **기반 시스템**(스택, 콘텐츠 스키마, 정확성 파이프라인)이다. Phase 0~1에서 구현한다.
- §6~8은 **콘텐츠와 위젯의 전체 스펙**이다. 챕터를 만들 때마다 해당 항목을 다시 연다.
- §10은 **실행 순서**다. Phase를 건너뛰지 않는다. 각 Phase의 DoD(Definition of Done)를 전부 충족해야 다음 Phase로 간다.
- §11은 **작업 규칙**이다. 특히 "사실을 지어내지 않는다" 규칙(§11.2)은 이 프로젝트의 존재 이유와 직결되므로 절대 어기지 않는다.

이 프로젝트에서 가장 중요한 두 가지 가치는 **정확성**과 **조작 가능성**이다. 예쁜데 부정확한 챕터보다, 투박해도 정확하고 만질 수 있는 챕터가 항상 낫다.

## 1. 프로젝트 개요

### 1.1 한 줄 정의

> LLM을 기초부터 심화까지, 읽는 게 아니라 **만지면서** 배우는 한국어 학습 사이트.

장기 비전: 이 사이트는 "AI를 만지면서 배우는 플랫폼"의 **1호 트랙(LLM)** 이다. 딥러닝·ML 등 트랙 확장은 §13 — 단, 실행은 LLM 트랙 완성이 먼저다.

### 1.2 배경과 포지셔닝

- 영어권에는 Transformer Explainer(Georgia Tech), LLM Visualization(BbyCroft), AnimatedLLM 등 논문급 인터랙티브 시각화 도구가 이미 존재한다. **트랜스포머 내부 시각화 단품으로는 경쟁하지 않는다.**
- 한국어권은 텍스트 교재(위키독스류), 번역 문서(IBM/AWS/Google), 유료 영상 강의(패스트캠퍼스/인프런)가 전부이며, **인터랙티브 + 커리큘럼 + 한국어**를 모두 갖춘 곳은 없다. 이 교집합이 우리의 자리다.
- 차별화 축 3개:
  1. **한국어 자체가 콘텐츠**: 한국어 토큰화의 비효율, 한국어 예문 기반 어텐션 등 영어권 도구가 구조적으로 못 하는 것.
  2. **조작 가능한 본문**: 모든 챕터에 위젯 1개. Explorable Explanations 계열의 문법.
  3. **엔지니어링 심화**: "내 GPU에 올라가나", "왜 느려지나" 등 수식이 아닌 실전이 심화의 정의. 재성의 RTX 3080 실측 경험이 근거.

### 1.3 타깃 사용자

| 페르소나 | 상태 | 이 사이트에서 얻는 것 |
|---|---|---|
| P1. 호기심 있는 일반인 | ChatGPT는 쓰지만 원리는 모름 | 파트 1~2 기본 레이어로 "아 그래서 그랬구나" |
| P2. 비AI 개발자 | 코딩은 하지만 ML 배경 없음 | 개발자 토글로 수식·코드까지, 파트 5~6으로 실전 |
| P3. AI 입문 학습자 | 강의·논문 사이에서 헤맴 | 논문 정독 시리즈, 용어사전, 검증된 레퍼런스 |

기본 본문은 항상 P1이 읽을 수 있는 수준으로 쓴다. P2·P3은 토글로 흡수한다.

### 1.4 성공 기준

- **품질**: 모든 공개 챕터가 §5의 5게이트를 통과. 공개 후 발견되는 사실 오류를 이슈로 추적하고 72시간 내 수정.
- **완성**: 6파트 24챕터 + 용어사전 50개 + 부록 타임라인 + 도구 3종이 전부 공개된 상태 (Phase 6 완료).
- **체감**: 챕터당 위젯 조작 없이는 본문이 성립하지 않는 구조 유지 (위젯이 장식이면 실패).
- **성장(부차)**: 계산기·토크나이저 등 도구 페이지의 검색 유입. 수익화는 비목표(§1.5).

### 1.5 비목표 (Non-goals)

- 게임화(포인트, 랭킹, 데일리 챌린지): **나중 단계**. 뼈대 완성 전에는 만들지 않는다.
- 회원 시스템·커뮤니티: 진도 저장은 localStorage로 충분. Supabase 연동은 결정 대기(§12).
- 실시간 LLM API 호출 기능: 운영 비용이 발생하는 기능은 만들지 않는다. 모든 위젯은 브라우저 연산 또는 사전계산 데이터로 동작한다(§3.3).
- 영어 버전: 한국어 단일 언어.
- 최신 뉴스/모델 리뷰 콘텐츠: 에버그린 원리 교육에 집중. 시효성 정보는 데이터 파일로 격리(§4.4).
- 트랙 2(딥러닝 등) 조기 착수: LLM 트랙 완성 전 금지. 단 §13의 확장 대비 3종(브랜드·track 필드·URL 규칙)은 비용이 0에 가까우므로 지금 적용한다.

## 2. 핵심 설계 원칙 (11원칙)

구현·콘텐츠 작성 중 판단이 갈리면 이 원칙으로 돌아온다.

1. **위젯 먼저, 설명 나중.** 챕터는 훅 질문 → 위젯 조작 → 설명 순서다. 독자가 현상을 먼저 목격하게 한다.
2. **챕터당 위젯 정확히 1개.** 0개면 교과서고, 2개면 산만하다. 위젯 없이 성립하는 챕터는 챕터가 아니라 용어사전 항목이다.
3. **난이도는 분리하지 않고 토글한다.** 기본(직관) / 개발자(수식·코드) / 연구(원문·논쟁) 3레이어를 같은 페이지에 접어 넣는다.
4. **역사는 연표가 아니라 탄생 스토리로.** 모든 기술은 이전 기술의 실패 지점에서 등장시킨다. 총정리 수요는 부록 타임라인이 받는다.
5. **모든 예문은 한국어.** 영어 예문이 필요한 경우(원 논문 인용 등)에만 병기한다.
6. **주장에는 출처, 수치에는 계산기, 실행에는 실측.** §5.2의 주장 3분류를 따른다.
7. **시효성 정보는 본문에 쓰지 않는다.** "현재 최고 모델" 류는 `data/facts/`로 격리하고 본문은 원리만 담는다.
8. **GPU 서버 없음.** 모든 인터랙션은 정적 호스팅 + 브라우저 연산으로 완결된다. 무거운 모델 로딩은 사용자의 명시적 클릭 뒤에만.
9. **챕터의 끝은 다음 챕터의 질문.** 모든 챕터는 연결 질문으로 끝나 서사를 만든다.
10. **모르면 지어내지 않고 표시한다.** 확신 없는 사실은 `<!-- TODO-VERIFY: ... -->` 마커를 남기고, 이 마커가 있는 문서는 CI가 배포를 차단한다(§4.5).
11. **시각 자료도 주장이다.** 다이어그램·표·예시 수치는 텍스트보다 더 신뢰받고 오래 기억되므로, 텍스트와 동일한 검증 게이트를 통과한다. 검증 불가능한 형태(출처 없는 외부 이미지, 코드가 아닌 그림 파일)는 쓰지 않는다. 상세는 §4.6.

### 3.2 위젯 아키텍처 — 레지스트리 패턴

재성의 금융계산기 사이트에서 검증된 패턴을 그대로 쓴다.

```
src/widgets/
├── registry.ts          # id → { component(lazy), meta } 매핑
├── types.ts             # WidgetMeta, WidgetProps 공통 타입
├── tokenizer/           # 위젯 하나 = 폴더 하나 (완결성)
│   ├── index.tsx        # 컴포넌트 (default export)
│   ├── meta.ts          # { id, title, description, dataDeps, sizeBudgetKB }
│   ├── logic.ts         # 순수 함수 (UI와 분리 — 골든 테스트 대상)
│   └── logic.test.ts    # 골든 테스트 (§5.6)
├── vram-calc/
└── ...
```

규칙:
- MDX에서는 `<Widget id="tokenizer" />` 한 줄로 삽입한다. 챕터 frontmatter의 `widgetId`와 일치해야 하며 불일치 시 빌드 에러.
- 모든 위젯은 `next/dynamic`으로 lazy load. 로딩 중 스켈레톤(위젯 실제 높이와 유사하게)을 보여 레이아웃 시프트를 막는다.
- **계산 로직은 반드시 `logic.ts` 순수 함수로 분리**한다. UI 없이 테스트 가능해야 하고, 이것이 §5.6 골든 테스트의 전제다.
- 위젯은 도구 페이지(`/tools/*`)에서 단독 페이지로도 렌더링된다(챕터 임베드와 컴포넌트 공유). 검색 유입용.
- 모바일 우선: 모든 조작은 터치로 가능해야 한다. hover에만 의존하는 인터랙션 금지.

### 3.3 데이터 전략 — 3계층

위젯의 데이터/연산은 아래 3계층 중 하나로 분류하고, 각 위젯 스펙(§8)에 계층을 명시한다.

| 계층 | 방식 | 사용처 | 비용 |
|---|---|---|---|
| **L1. 라이브 계산** | 브라우저에서 순수 JS 계산 | 토크나이저, VRAM 계산기, 샘플링(로짓 재가공), 양자화 수직선, LoRA 계산기 | 0 |
| **L2. 사전계산 트레이스** | Python으로 실제 모델을 돌려 결과를 JSON으로 저장, 위젯은 재생만 | 다음 토큰 분포, 어텐션 행렬, 임베딩 2D 좌표, 층별 표현 변화, 베이스vs채팅 비교 | 0 (빌드 자산) |
| **L3. 브라우저 모델** | transformers.js로 소형 ONNX 모델을 사용자 클릭 후 로딩 | "직접 해보기" 스트레치 모드 (다음 토큰 라이브, RAG 임베딩 검색) | 0 (사용자 대역폭) |

원칙:
- **모든 챕터는 L1 또는 L2만으로 완결**되어야 한다. L3은 항상 "보너스 모드"이며, 로딩 실패·미지원 브라우저에서도 챕터 학습에 지장이 없어야 한다.
- L2 트레이스는 `scripts/precompute/`의 스크립트로 생성하며, JSON 상단에 생성 메타(모델명, 버전, 날짜, 스크립트 커밋 해시)를 포함한다. 이것이 곧 해당 데이터의 출처 표기가 된다.
- L2용 모델 선정(한국어 소형 GPT 등)은 §8.3과 §12 참조.

```
    └── templates/VERIFY.md  # 검증 프롬프트 템플릿 (§5.5)
```

**URL 규칙(멀티트랙 대비)**: 커리큘럼 라우트는 트랙 프리픽스를 갖는다 — `/llm/token`, `/llm/attention`. 용어사전(`/glossary`)·도구(`/tools/*`)·타임라인은 트랙 공용 전역 자원으로 프리픽스 없음. 트랙 2가 생겨도 기존 URL이 단 하나도 이동하지 않게 하기 위한 선제 규칙이다.

### 3.5 성능 예산

- 챕터 페이지 초기 JS(위젯 청크 제외): **150KB gzip 이하**.
- 위젯 청크: 개별 **80KB gzip 이하** (d3 등 의존성 포함 시 부분 임포트로 맞출 것).
- L2 트레이스 JSON: 챕터당 **300KB 이하**. 초과 시 데이터를 줄이거나 분할 로딩.
- L3 모델 다운로드: 반드시 명시적 버튼("모델 불러오기 · 약 NN MB") 뒤에서만. 진행률 표시 필수.
- LCP 2.5초 이내(모바일 4G 기준), CLS 0.1 이하 — 위젯 스켈레톤 높이 고정으로 달성.

## 4. 콘텐츠 시스템

### 4.1 챕터 frontmatter 스키마 (Zod로 강제)

모든 커리큘럼 MDX는 아래 스키마를 통과해야 빌드된다. 필드 누락·형식 위반은 **빌드 에러**다.

```ts
// velite.config.ts 내 스키마 (개념 정의 — 구현 시 세부 조정 가능하나 필드 삭제 금지)
const chapter = s.object({
  id: s.string(),                    // 예: "1-1" (파트-챕터)
  track: s.string(),                 // 트랙 slug — 현재 "llm" 고정. §13 멀티트랙 대비
  slug: s.string(),                  // URL — 예: "token"
  part: s.number().min(1).max(6),
  order: s.number(),
  title: s.string(),                 // 예: "토큰: AI가 읽는 글자"
  hook: s.string(),                  // 훅 질문 1문장 — 예: "ChatGPT는 왜 'ㄹ'이 몇 개인지 못 셀까?"
  ahaMoment: s.string(),             // 이 챕터의 아하 모먼트 1문장 (내부 품질 기준용)
  widgetId: s.string(),              // src/widgets/registry.ts 에 존재해야 함 — 린트 검사
  prerequisites: s.array(s.string()),// 선수 챕터 id 배열
  nextHook: s.string(),              // 다음 챕터로의 연결 질문
  glossaryTerms: s.array(s.string()),// 이 챕터가 링크하는 용어 slug — 존재 검사
  references: s.array(s.string()).min(1), // references.yaml 의 키 — 최소 1개, 존재 검사
  lastVerified: s.string(),          // "2026-07-07" — 검증 게이트 통과일. 페이지에 배지로 노출
  status: s.enum(["draft","verified","published"]),
  depthLevels: s.array(s.enum(["basic","dev","research"])), // 이 챕터가 제공하는 레이어
})
```

`status` 의미: `draft`(집필 중, 프로덕션 빌드에서 제외) → `verified`(§5 게이트 4까지 통과) → `published`(재성 최종 승인). 프로덕션에는 `published`만 노출한다.

### 4.2 MDX 커스텀 컴포넌트

챕터 본문에서 사용하는 컴포넌트. Phase 0에서 전부 구현한다.

| 컴포넌트 | 역할 | 규칙 |
|---|---|---|
| `<Widget id="..." />` | 위젯 삽입 | 챕터당 1회. frontmatter `widgetId`와 일치 검사 |
| `<Depth level="dev">…</Depth>` | 개발자 레이어 (수식·PyTorch 코드) | 접힌 상태가 기본. 열림 상태는 URL 쿼리로 공유 가능하게 |
| `<Depth level="research">…</Depth>` | 연구 레이어 (원문 인용·논쟁 지점) | 원문 인용은 15단어 미만 + 출처 링크 필수 |
| `<Term slug="...">softmax</Term>` | 용어사전 링크 | hover/tap 시 한 줄 정의 팝오버 + 상세 페이지 링크 |
| `<CheckQuestion answer="...">…</CheckQuestion>` | 챕터 말미 확인 질문 1개 | 채점 없음 — 탭하면 답이 열리는 형태. 부담 최소화 |
| `<NextHook />` | frontmatter의 `nextHook` + 다음 챕터 링크 렌더 | 모든 챕터의 마지막 요소 |
| `<Refs />` | frontmatter `references`를 참고문헌 섹션으로 렌더 | `<NextHook />` 바로 앞 |
| `<FactValue id="gpt4o.context" />` | 시효성 수치 삽입 (§4.4) | 본문에 시효성 숫자 하드코딩 금지 — 린트 검사 대상 |
| `<Figure src caption />` | 정적 그림·다이어그램·표의 래퍼 | 캡션·alt 필수. §4.6 시각 자료 정책 적용 |
| `<Prereq />` | frontmatter `prerequisites`를 챕터 상단 안내 상자로 렌더 | 잠금 아님 — "이 챕터는 OO(2-1)을 알면 더 잘 읽힙니다. 몰라도 괜찮고, 막히면 여기로" 톤. 선수 챕터 없으면 미렌더 |

챕터 본문 표준 골격 (이 순서를 지킨다):

```mdx
{/* 1. 훅 — frontmatter hook이 페이지 상단에 자동 렌더 */}
<Prereq />  {/* 선수 챕터 안내 — 잠금 아님. 없으면 자동 생략 */}
{/* 2. 도입 2~4문단: 훅을 구체화, 위젯으로 초대 */}
<Widget id="tokenizer" />
{/* 3. 조작 가이드: "이렇게 해보세요" 2~3개 (위젯 바로 아래) */}
{/* 4. 본문: 위젯에서 목격한 현상을 설명. 훅 회수(아하 모먼트) 포함 */}
<Depth level="dev">…</Depth>
<Depth level="research">…</Depth>
{/* 5. 마무리 */}
<CheckQuestion …/>
<Refs />
<NextHook />
```

### 4.3 용어사전 스키마

```ts
const glossaryTerm = s.object({
  slug: s.string(),          // "softmax"
  term: s.string(),          // "소프트맥스 (softmax)"
  oneLiner: s.string(),      // 팝오버용 1문장 정의 (60자 이내)
  relatedChapters: s.array(s.string()),
  references: s.array(s.string()).min(1),
  lastVerified: s.string(),
  status: s.enum(["draft","verified","published"]),
})
```

본문은 자유 형식이되 300~800자 + 필요 시 수식/그림 1개. 용어사전은 위키형 상호 링크를 적극 사용한다(파고들수록 계속 나오는 구조가 '방대함'의 체감을 만든다).

### 4.4 시효성 데이터 (`data/facts/`)

낡을 수 있는 모든 수치는 본문이 아니라 facts JSON에 산다.

```jsonc
// data/facts/models.json (예시 구조)
{
  "_meta": { "lastVerified": "2026-07-07", "verifiedBy": "재성" },
  "gpt4o": { "context": 128000, "note": "OpenAI 공식 문서 기준", "sourceRef": "openai-docs-models" },
  ...
}
```

- 본문에서는 `<FactValue id="gpt4o.context" />`로만 참조한다.
- 각 facts 파일의 `_meta.lastVerified`가 90일을 넘기면 빌드 시 **경고**를 출력한다(차단은 아님 — 재검증 리마인더 역할).
- 페이지 하단 배지: "이 페이지의 원리 설명 검증일 / 수치 데이터 검증일"을 각각 표기.

### 4.5 콘텐츠 린트 (CI — 배포 차단 조건)

`scripts/lint-content.ts`를 CI에서 실행. 아래 위반은 **빌드 실패**:

1. frontmatter 스키마 위반 (Velite가 자동 처리)
2. 본문에 `TODO-VERIFY` 마커 잔존 (`status: published` 문서에 한함)
3. `widgetId`가 레지스트리에 없음
4. `<Term slug>`·`glossaryTerms`가 용어사전에 없음 (draft 용어는 경고)
5. `references` 키가 `references.yaml`에 없음
6. published 챕터의 `lastVerified` 누락
7. 본문에 4자리 이상 숫자+단위 패턴이 `<FactValue>` 밖에서 발견 (휴리스틱 — 경고 수준, 화이트리스트 허용: 연도, 논문 수치 인용 등)

### 4.6 시각 자료 정책 (원칙 11의 실행)

다이어그램·표·이미지·예시는 이해를 돕는 최우선 수단이되, 전부 검증 가능해야 한다.

1. **다이어그램은 코드로만 존재한다.** 인라인 SVG 컴포넌트(디자인 토큰 색 사용 — 다크모드 자동 대응) 또는 리포 내 소스 파일. 비트맵 그림 산출물 금지 — diff·리뷰·게이트 3 검증이 불가능하기 때문. 원 논문 그림은 저작권상 재게재 금지 — **재구성(redraw)** 하고 캡션에 "OO(연도) Figure N을 재구성" 표기. 시각 문법은 DESIGN §5.6.
2. **표는 적극 사용한다.** 비교·정리·분류에 표가 산문보다 낫다면 표를 쓴다. MDX 테이블(검증 용이). 단 시효성 수치는 facts 파일에서 렌더 — 표에 하드코딩 금지(§4.4).
3. **이미지는 직접 캡처한 실증만.** 실제 현상의 스크린샷(딸기 사례 등)은 최고의 교육 자료 — 캡처 일자 표기. 외부 이미지·스톡·AI 생성 일러스트는 전면 금지(저작권 + 검증 불가 + DESIGN §1.3).
4. **예시 수치는 지어내지 않는다.** 본문의 숫자 예시는 실제 소스 우선 — L2 트레이스에서 뽑은 실제 값을 쓰고 출처를 캡션으로 단다. 손계산용 단순 예제는 허용하되 "장난감 예제(실제 모델 값 아님)"를 명시한다. 그럴듯한 창작 수치는 금지.
5. 모든 시각 자료는 게이트 3 검증 대상이다(구조도의 방향·순서·라벨, 표·예시의 수치 전수 — §5.5 항목 6).

### 4.7 채집 모드와 콘텐츠 백로그

재성(첫 독자)이 사이트로 공부하다 생긴 궁금증을 그 자리에서 백로그로 만드는 시스템. **독자에게는 존재 자체가 비노출** — 용어사전 미등재 단어는 평문으로 렌더되며, 스텁·"준비 중" 표시를 독자에게 절대 보여주지 않는다(미완성으로 보이면 안 됨).

- **활성화**: localStorage 플래그로 재성만 켠다(숨은 진입 방식은 구현 재량 — 예: 일러두기 하단 버전 표기 7연타). 플래그 없으면 관련 UI가 일절 렌더되지 않는다.
- **채집**: 본문 텍스트 선택 → "백로그에 추가" 플로팅 버튼 → `{용어, 출처(챕터·문단 앵커), 메모, 일시}`를 localStorage에 축적 → "내보내기"로 JSON 복사 → 리포 `data/backlog.json`에 수동 병합.
- **소비**: Claude Code 세션에서 backlog.json 항목을 용어사전·챕터 보강의 SPEC으로 전환(5게이트 동일 적용). 새 용어가 published되면 기존 본문의 해당 `<Term>`이 자동으로 살아난다 — 사이트가 궁금증의 순서대로 자라는 구조.
- **독자 채널(런칭 후)**: 챕터 하단 오류 제보 링크에 "이해 안 되는 부분 알려주기"를 추가해 같은 백로그로 합류시킨다. 이는 미완성 고백이 아니라 피드백 수집이므로 신뢰 톤과 충돌하지 않는다.
- 용어사전 초기 50개(§7.1)는 시드일 뿐이다. 이후 확장은 백로그의 수요 순서를 따른다.

## 5. 정확성 파이프라인

이 사이트의 존재 이유. **정확성은 검수 의지가 아니라 프로세스로 보장한다.**

### 5.1 출처 위계와 references.yaml

모든 챕터·용어는 근거를 아래 위계에서 취한다.

| 등급 | 출처 | 용도 |
|---|---|---|
| S1 | 원 논문 (arXiv/학회) | 아키텍처·알고리즘·학습 기법의 근거. **각 챕터는 S1을 최소 1개 가져야 함** (실전 챕터는 예외 허용 — §6에 명시) |
| S2 | 공식 문서·테크니컬 리포트 (HuggingFace, PyTorch, OpenAI/Anthropic/Meta 공식) | API·수치·구현 세부 |
| S3 | 검증된 2차 자료 (Karpathy 강의/nanoGPT, Jay Alammar, 3Blue1Brown, 대학 공개 강의) | 설명 방식·직관 참고. 사실의 근거로는 S1/S2 필요 |
| X | 개인 블로그, 나무위키, 커뮤니티 | **근거로 사용 금지.** 표현 아이디어 참고만 |

```yaml
# data/refs/references.yaml (예시 항목)
vaswani2017:
  type: paper            # paper | docs | secondary
  title: "Attention Is All You Need"
  authors: "Vaswani et al."
  year: 2017
  url: "https://arxiv.org/abs/1706.03762"
  grade: S1
```

`<Refs />`가 이 DB에서 렌더링한다. **참고문헌은 숨기지 않고 모든 챕터 하단에 노출한다** — 한국어 LLM 콘텐츠 중 논문 단위 출처를 밝히는 곳이 거의 없으므로 이것 자체가 신뢰 차별화다.

### 5.2 주장 3분류와 검증 방법

| 분류 | 예 | 검증 방법 |
|---|---|---|
| A. 에버그린 사실 | "셀프 어텐션은 모든 토큰 쌍의 관계를 계산한다" | S1 원문 대조 (게이트 3) |
| B. 수치 주장 | "7B 모델은 FP16으로 약 14GB" | **위젯이 직접 계산해서 보여준다.** 본문 수치와 위젯 출력이 일치해야 함. 위젯 로직은 골든 테스트(§5.6)로 고정 |
| C. 실행 주장 | "RTX 3080 10GB에서 Q4 양자화 7B가 돌아간다" | **재성 실측만 게재.** 실측 로그(모델/양자화/속도/날짜)를 `data/facts/bench-3080.json`에 기록하고 그 파일만 참조 |

B의 핵심: **위젯을 정확성의 앵커로 쓴다.** 위젯이 실제 토크나이저·실제 수식으로 동작하면, 본문에 오타가 나도 위젯은 거짓말을 못 한다. 본문과 위젯이 상호 검증한다.

### 5.3 생산 워크플로 — 5게이트

챕터 하나는 아래 게이트를 순서대로 통과해야 `published`가 된다.

```
게이트 1  SPEC     재성(또는 재성+Claude)이 docs/templates/SPEC.md 로 챕터 스펙 확정
게이트 2  DRAFT    Claude Code가 SPEC + S1/S2 원문을 근거로 본문·위젯 초안 작성 (status: draft)
게이트 3  VERIFY   ★별도 세션★에서 docs/templates/VERIFY.md 프롬프트로 초안↔원문 대조.
                   지적 사항을 전부 수정하거나 TODO-VERIFY 마커로 남김
게이트 4  TEST     위젯 골든 테스트 통과 + 콘텐츠 린트 통과 (status: verified)
게이트 5  REVIEW   재성이 실제로 읽고 위젯을 조작해본 뒤 승인 (status: published, lastVerified 갱신)
```

게이트 3을 **작성 세션과 분리된 새 세션**에서 돌리는 이유: 같은 컨텍스트에서는 모델이 자기 초안을 자기가 쓴 근거로 옹호하는 편향이 생긴다. 검증 세션에는 초안과 원문 출처만 넣는다.

### 5.4 챕터 SPEC 템플릿 (`docs/templates/SPEC.md`)

```md
# SPEC: [챕터 id] [제목]
## 훅 질문
## 아하 모먼트 (독자가 챕터를 닫으며 얻는 한 문장)
## 위젯
- id / 데이터 계층(L1/L2/L3) / 핵심 조작 / 조작 가이드 3개
```

### 5.6 골든 테스트

계산형 위젯(L1)의 `logic.ts`는 알려진 정답 케이스로 고정한다. 사주 사이트의 golden test case 방식과 동일.

예 — `vram-calc/logic.test.ts`:
```
7B  × FP16            → 가중치 14.0 GB (±0.5)
7B  × Q4_K_M(≈4.5bit) → 가중치 ≈ 4.1 GB
KV캐시: Llama-2-7B 구성(32층·32헤드·128dim·FP16)에서 4096 토큰 → 2×32×32×128×4096×2B = 2.0 GiB
```
정답값의 근거(공식 문서·논문·llama.cpp 산식)를 테스트 파일 주석에 남긴다. 토크나이저 위젯은 대표 문장 10개의 토큰 수를 스냅샷으로 고정한다(라이브러리 업데이트로 인코딩이 바뀌면 테스트가 알려줌).

### 파트 1 — 직관 (3챕터) 【파일럿 · 최대 해상도】

파트 1 전체의 문지방 문장(1-1 도입 첫 문단에 배치): **"ChatGPT가 하는 일은 단 하나, 글 조각들을 보고 다음에 올 조각을 맞히는 것이다. 그럼 그 '조각'이 뭔지부터 보자."** — 정의를 챕터로 만들지 않고 한 문장으로 압축해 토큰 챕터의 입구로 쓴다. 'LLM'이라는 용어는 이 문장 직후 한 줄로 넘겨받는다("이런 AI를 LLM(대형 언어 모델)이라 부른다") — §11.3 어휘 다리 규칙 적용. P1 독자의 어휘에는 'ChatGPT'는 있어도 'LLM'은 없다는 전제로 쓴다.

#### 1-1 토큰: AI가 읽는 글자 (`slug: token`)

- **훅**: "ChatGPT는 왜 '딸기'에 ㄹ이 몇 개인지 못 셀까?" (strawberry-r 밈의 한국어판. 도입에 실제 실패 스크린샷 1장 — 재성이 직접 캡처해 제공)
- **위젯**: `w-tokenizer` (L1) — §8.2.1 상세 스펙
- **아하**: 모델의 눈에 '딸기'는 글자들이 아니라 숫자 한두 개다. 안이 안 보이니 셀 수 없다.
- **흐름**:
  1. 문지방 문장(ChatGPT 어휘로 시작 — LLM이라는 단어는 번역 병기 후에만) + 훅 구체화 (2~3문단)
  2. 위젯: 아무 문장이나 넣어 쪼개보기
  3. 조작 가이드: ① "안녕하세요"와 "hello"를 넣고 토큰 수를 비교하라 ② 자기 이름을 넣어보라 ③ "딸기"를 넣고 몇 조각인지 보라
  4. 설명: 토큰=서브워드 조각, BPE의 직관(자주 붙어 나오는 조각을 병합), 글자·단어·토큰의 차이
  5. 한국어의 비용: 같은 뜻이라도 한국어가 토큰을 더 쓴다 → API 요금·컨텍스트 소모로 직결 (Petrov 2023 근거)
  6. 훅 회수: 토큰 ID의 세계에는 'ㄹ'이 존재하지 않는다
- **깊이** — dev: BPE 병합 알고리즘 의사코드, 바이트 폴백(한글이 UTF-8 바이트로 쪼개지는 경우) / research: Sennrich 2016 원문에서 BPE 도입 동기, Petrov 2023의 언어 간 불공정 수치
- **역사 훅**: 없음 (첫 챕터는 가볍게)
- **출처**: `sennrich2016`(S1, BPE), `petrov2023`(S1, 토크나이저 언어 불공정), `openai-tokenizer-docs`(S2)
- **연결**: "글이 숫자 조각이 됐다. 모델은 이 숫자들로 뭘 하는가?"

#### 1-2 다음 토큰 맞히기: LLM의 유일한 일 (`slug: next-token`)

- **훅**: "'오늘 점심은 김치…' 다음에 올 말, 당신도 이미 알고 있다. LLM이 하는 일이 정확히 그것이다."
- **위젯**: `w-next-token` (L2, 스트레치 L3) — §8.2.2 상세 스펙
- **아하**: ChatGPT의 모든 능력은 "다음 토큰 확률 분포"라는 단 하나의 출력에서 나온다. 대화·번역·코딩은 전부 이 게임의 변형이다.
- **흐름**: 훅(사람도 하는 게임) → 위젯(문장을 고르고 한 스텝씩 진행, top-5 확률 막대 관찰) → 조작 가이드: ① 확률이 한쪽으로 쏠리는 지점과 팽팽한 지점을 찾아라 ② 내 예상과 모델 top-1이 다른 지점을 찾아라 → 설명: 언어모델의 정의, 자기회귀 생성(한 토큰씩 이어 붙이는 루프), "확률 분포"가 출력의 전부라는 사실 → 훅 회수
- **깊이** — dev: logit → softmax → 확률의 흐름(수식), 어휘 크기만큼의 벡터라는 것 / research: Shannon의 언어 예측 게임(1951)과의 연결, GPT-2 논문의 "언어모델은 비지도 멀티태스크 학습자" 관점
- **역사 훅**: Shannon 게임 한 단락 — "이 게임은 1951년에 사람으로 이미 실험됐다"
- **출처**: `radford2019`(S1, GPT-2), `shannon1951`(S1), `bengio2003`(S1, 신경 언어모델 — research 레이어)
- **연결**: "그럴듯한 다음 토큰을 고르려면 단어의 '의미'를 알아야 한다. 숫자에 불과한 토큰이 어떻게 의미를 갖지?"

#### 1-3 임베딩: 의미를 좌표로 (`slug: embedding`)

- **훅**: "'왕 − 남자 + 여자 = ?' — 단어로 산수가 된다면 믿겠는가?"
- **위젯**: `w-embedding-map` (L2) — §8.2.3 상세 스펙
- **아하**: 의미란 좌표다. 비슷한 뜻 = 가까운 위치. 모델이 배우는 것은 결국 이 지도다.
- **흐름**: 훅 → 위젯(한국어 단어 수백 개의 2D 지도 탐색, 검색·이웃 하이라이트, 유추 데모) → 조작 가이드: ① '서울'을 검색하고 이웃을 보라 ② 감정 단어들이 모인 대륙을 찾아라 ③ 왕−남자+여자 버튼을 눌러라 → 설명: 원-핫의 한계 → 밀집 벡터, 거리=유사도, 이 지도가 학습으로 만들어진다는 예고 → 2D는 수백 차원의 그림자라는 정직한 각주
- **깊이** — dev: 코사인 유사도 수식, 임베딩 행렬(vocab×dim)이 모델의 첫 층이라는 것 / research: word2vec 원문(Mikolov 2013)의 유추 실험, 정적 임베딩 vs 문맥 임베딩의 차이(다음 파트 예고)
- **역사 훅**: word2vec(2013)이 "의미를 좌표로" 시대를 연 사건 — 한 단락
- **출처**: `mikolov2013`(S1), `jurafsky-slp3`(S2, 교과서 — 벡터 의미론 장)
- **연결(=파트 연결)**: "단어마다 좌표가 있다 치자. 그런데 '배(먹는)'와 '배(타는)'는 같은 좌표일 수 없다. 문맥을 반영하려면? — 여기서 어텐션이 등장한다."

### 파트 2 — 구조 (5챕터)

#### 2-1 어텐션: 서로를 쳐다보는 단어들 (`slug: attention`)

- **훅**: "'나는 배를 타고 가며 배를 먹었다' — 당신은 두 '배'를 어떻게 구분했나?"
- **위젯**: `w-attention` (L2) — 큐레이션된 한국어 문장 ~10개의 실제 어텐션 가중치. 토큰을 탭하면 그 토큰이 다른 토큰들을 쳐다보는 세기가 선 굵기/색으로 표시. 레이어·헤드 셀렉터.
- **아하**: 문맥 반영 = 주변 단어들을 가중치로 섞는 것. '배'의 벡터가 '타고' 쪽을 강하게 쳐다보며 '선박'의 의미로 물든다.
- **역사 훅**: **이 챕터가 RNN 역사를 소화한다.** 도입 3~4문단: 옛 모델은 문장을 한 단어씩 순서대로 읽었고(RNN), 길어지면 앞을 잊었다 → 잊지 않으려는 개선(LSTM)도 한계 → 2017년, "순서대로 읽기를 아예 버리고 모든 단어가 모든 단어를 동시에 보게 하자"(트랜스포머). 박스 다이어그램 없이 이야기로만.
- **깊이** — dev: 유사도(내적)→softmax→가중합이라는 3단계를 장난감 숫자 예제로 손계산 / research: Vaswani 2017 §3.2 원문, Bahdanau 2014(어텐션의 최초 형태)
- **출처**: `vaswani2017`(S1), `bahdanau2014`(S1), `hochreiter1997`(S1, LSTM — 역사 훅 근거)
- **연결**: "쳐다볼 상대와 세기는 무엇이 정하나? Q·K·V라는 세 벌의 변환이다."

#### 2-2 멀티헤드: 여러 관점으로 보기 (`slug: multi-head`)

- **훅**: "같은 문장을 문법 선생님, 번역가, 시인이 각자 다르게 읽는다. 모델 안에도 그런 '읽기 담당자'가 수십 명 있다."
- **위젯**: `w-attention`의 확장 모드 — 같은 문장에 대해 여러 헤드의 어텐션 패턴을 그리드로 비교. (신규 위젯이 아니라 2-1 위젯의 다른 진입점 — 위젯 1개 원칙은 "챕터당 1개 임베드"로 해석하며, 컴포넌트 재사용은 허용)
- **아하**: 헤드마다 다른 관계(수식 관계, 인접성, 특정 품사 추적 등)를 본다. Q·K·V는 "무엇을 찾고(Q), 무엇으로 검색되며(K), 무엇을 건네줄지(V)"의 역할 분담이다.
- **깊이** — dev: QKV 행렬 곱 차원 추적, 멀티헤드의 분할·결합 / research: Vaswani 2017의 헤드 수 선택, 헤드 해석 연구(예: Clark 2019 "What Does BERT Look At?")의 한계 — 해석은 부분적이라는 정직한 단서
- **출처**: `vaswani2017`(S1), `clark2019`(S1)
- **연결**: "쳐다보고 섞는 것까지 했다. 그런데 섞기만 하면 생각은 누가 하나?"

#### 2-3 FFN과 잔차연결: 생각하는 층, 잊지 않는 길 (`slug: ffn-residual`)

- **훅**: "트랜스포머 파라미터의 약 3분의 2는 어텐션이 아니라 이름도 밋밋한 'FFN'에 있다. 얘가 뭐길래?"
- **위젯**: `w-layer-flow` (L2) — 한 토큰의 표현이 층을 지나며 얼마나 변하는지(층간 코사인 유사도)를 사전계산 데이터로 시각화. 잔차연결 개념은 "지름길이 있는 그림/없는 그림" 토글 애니메이션으로.
- **아하**: 어텐션이 '정보 수집'이라면 FFN이 '개별 가공'이다. 잔차연결은 층을 아무리 쌓아도 원본 정보가 사라지지 않게 하는 고속도로다.
- **깊이** — dev: FFN 수식(확장→활성화→축소), LayerNorm의 위치, 잔차 스트림 관점 / research: He 2016(ResNet, 잔차의 기원), FFN을 키-밸류 메모리로 보는 연구(Geva 2021) 소개
- **출처**: `vaswani2017`(S1), `he2016`(S1), `geva2021`(S1, research)
- **연결**: "그런데 이상하다. 모든 단어가 모든 단어를 '동시에' 본다면, 모델은 어순을 어떻게 알지? '개가 사람을 물었다'와 '사람이 개를 물었다'는 다른데."

#### 2-4 위치의 문제: 순서를 아는 법 (`slug: positional`)

- **훅**: "'개가 사람을 물었다'와 '사람이 개를 물었다' — 어텐션만으로는 이 둘이 같아 보인다."
- **위젯**: `w-positional` (L1) — 사인·코사인 위치 인코딩 곡선 탐색기(위치 슬라이더 → 패턴 변화) + "어순 섞기" 미니 데모(같은 토큰 집합, 다른 순서 → 사전계산된 다음 토큰 예측 차이).
- **아하**: 순서 정보를 벡터에 '입혀서' 넣는다. 위치마다 고유한 무늬를 더해주는 것.
- **깊이** — dev: sin/cos 수식과 왜 이 함수인가(상대 위치의 선형 표현 가능성) / research: Vaswani 2017의 선택 근거 원문, 현대 모델의 RoPE(Su 2021)로의 이동 — 개념만, 상세는 용어사전
- **출처**: `vaswani2017`(S1), `su2021`(S1, RoPE)
- **연결**: "부품이 다 모였다. 토큰→임베딩→어텐션→FFN→…→확률. 이제 한 토큰의 전체 여행을 처음부터 끝까지 따라가 보자."

#### 2-5 전체 파이프라인: 한 토큰의 여행 (`slug: pipeline`)

- **훅**: "'대한민국의 수도는' 을 넣고 엔터를 치는 순간부터 '서'라는 글자가 화면에 찍히기까지, 정확히 무슨 일이 일어나는가."
- **위젯**: `w-pipeline` (L2) — **파트 2의 캡스톤.** 토큰화→임베딩→N개 층 통과→로짓→softmax→샘플→다음 토큰이 입력에 붙는 루프 전체를 스테퍼로 진행. 실제 소형 모델의 사전계산 트레이스 사용. 각 단계에서 해당 챕터로 점프 링크.
- **아하**: 파트 1~2에서 배운 모든 조각이 하나의 관으로 연결된다. 그리고 이 관은 매 토큰마다 처음부터 다시 돈다.
- **깊이** — dev: 텐서 차원이 단계별로 어떻게 변하는지 표 / research: 디코더-온리 구조가 표준이 된 맥락 (GPT 계열)
- **역사 훅**: 인코더-디코더에서 디코더-온리로 — BERT/GPT 분기의 예고편 반 단락 (본편은 3-1)
- **출처**: `vaswani2017`(S1), `radford2018`(S1, GPT-1)
- **연결(=파트 연결)**: "이 여행에서 쓰인 수십억 개의 가중치들 — 어텐션의 QKV, FFN의 행렬 — 은 대체 어디서 온 숫자들인가?"

### 파트 3 — 학습 (4챕터)

#### 3-1 사전학습: 인터넷을 압축하다 (`slug: pretraining`)

- **훅**: "정답지를 만든 사람이 아무도 없는데, 모델은 뭘 보고 배웠을까? — 답: 인터넷 전체가 정답지다."
- **위젯**: `w-training-progress` (L2) — 같은 프롬프트에 대해 학습 스텝별 체크포인트의 출력이 어떻게 변하는지 타임라인으로 관찰(자모 반복 → 단어 비슷한 것 → 문장 → 그럴듯한 글). 데이터는 재성이 nanoGPT 계열로 소형 한국어 모델을 학습하며 체크포인트별 출력을 캡처해 생성(§8.3, 재성 액션 아이템). 실패 시 폴백: 공개된 학습 로그 재구성 + 출처 명시.
- **아하**: "다음 토큰 맞히기"를 인터넷 규모로 시키면, 맞히기 위해 문법→사실→추론 비슷한 것까지 압축하게 된다. 라벨 없는 자기지도의 마법.
- **역사 훅**: **이 챕터가 BERT vs GPT를 소화한다.** 같은 트랜스포머에서 두 가족이 갈라졌다 — 빈칸 맞히기로 배운 BERT(이해 특화)와 다음 토큰으로 배운 GPT(생성 특화). 구조가 아니라 **학습 목표**의 차이라는 점을 강조. BERT는 여기서 끝나지 않고 6-2(RAG)에서 임베딩 모델의 조상으로 재등장한다는 복선을 명시적으로 깔 것.
- **깊이** — dev: 크로스 엔트로피 손실의 의미(놀람의 크기), 데이터셋 규모 감각 / research: GPT-2/3 원문에서 스케일과 능력의 관계, 스케일링 법칙(Kaplan 2020, Hoffmann 2022) 소개
- **출처**: `devlin2018`(S1, BERT), `radford2019`(S1), `brown2020`(S1, GPT-3), `kaplan2020`·`hoffmann2022`(S1, research)
- **연결**: "'배운다'고 계속 말했는데, 수십억 개의 숫자가 구체적으로 어떻게 조정되는 건가?"

#### 3-2 경사하강: 배운다는 것의 실체 (`slug: gradient-descent`)

- **훅**: "안개 낀 산에서 눈을 감고 골짜기를 찾는 법 — 발밑의 기울기만 느끼면 된다."
- **위젯**: `w-gradient-descent` (L1) — 고전이지만 최고의 조작감: 손실 지형(2D 등고선) 위 공, 학습률 슬라이더, 시작점 드래그. 학습률이 크면 발산하는 것을 직접 목격.
- **아하**: 학습 = 손실이 줄어드는 방향으로 가중치를 아주 조금씩 미는 것의 무한 반복. 신비가 아니라 미분이다.
- **깊이** — dev: 경사하강 수식, 역전파는 "기울기를 효율적으로 계산하는 방법"이라는 위상 정리(체인 룰 스케치) / research: 옵티마이저 진화(SGD→Adam) 한 단락, Rumelhart 1986
- **출처**: `rumelhart1986`(S1), `goodfellow-dlbook`(S2, 교과서), `kingma2014`(S1, Adam — research)
- **연결**: "인터넷을 통째로 배운 모델이 나왔다. 그런데 이 모델은 아직 '어시스턴트'가 아니다. 물어보면 대답 대신 질문을 이어 쓰기도 한다. 왜?"

#### 3-3 파인튜닝: 범용에서 전문으로 (`slug: finetuning`)

- **훅**: "의대 6년(사전학습)을 마친 사람도 전공의 수련(파인튜닝)을 거쳐야 진료를 본다."
- **위젯**: `w-base-vs-tuned` (L2) — 같은 프롬프트에 대한 베이스 모델 vs 인스트럭션 튜닝 모델의 출력 비교 브라우저(사전계산, 공개 모델 쌍으로 재성이 생성). 프롬프트 10여 개 큐레이션.
- **아하**: 베이스 모델은 "이어쓰기 기계"일 뿐이다. 지시를 따르는 성질은 타고나는 게 아니라 별도로 가르친 것이다.
- **깊이** — dev: 전체 파인튜닝의 비용 문제 제기(파라미터 전부를 다시 학습) — 5-4 LoRA의 복선 / research: 인스트럭션 튜닝 계보(FLAN, T0 등) 개요
- **출처**: `wei2021`(S1, FLAN), `ouyang2022`(S1 — SFT 단계 참조)
- **연결**: "지시는 따르게 됐다. 그런데 '더 좋은 답'과 '나쁜 답'의 차이는 누가 가르쳤나? GPT-3는 2020년에 이미 있었는데, 세상이 뒤집힌 건 왜 2022년 ChatGPT였나?"

#### 3-4 정렬: ChatGPT를 만든 마지막 재료 (`slug: alignment`)

- **훅**: "GPT-3(2020)와 ChatGPT(2022) 사이의 2년, 무엇이 달라졌나."
- **위젯**: `w-preference-ranking` (L2) — 같은 질문에 대한 답변 3개를 독자가 직접 순위 매기기 → "당신이 방금 한 일이 RLHF 데이터 라벨링이다" → InstructGPT의 사람 선호 데이터 규모와 함께 회수. 답변 세트는 사전계산/큐레이션.
- **아하**: 정렬 = "사람이 더 좋아하는 답"이라는 새로운 목표를 확률 게임 위에 얹은 것. 능력(사전학습)과 태도(정렬)는 다른 단계에서 만들어진다.
- **깊이** — dev: RLHF 3단계(SFT→보상모델→RL) 개요도, DPO가 이를 단순화한 아이디어 / research: Ouyang 2022 원문 수치(1.3B 정렬 모델이 175B 비정렬보다 선호됨), Rafailov 2023(DPO)
- **출처**: `ouyang2022`(S1, InstructGPT), `rafailov2023`(S1, DPO), `christiano2017`(S1, RLHF 기원 — research)
- **연결(=파트 연결)**: "이제 모델이 완성됐다. 그런데 완성된 모델이 실제로 답을 '생성'하는 순간에도 아직 우리가 모르는 선택들이 남아 있다. 같은 질문에 매번 다른 답이 나오는 이유부터."

### 파트 4 — 생성 (4챕터)

#### 4-1 샘플링: 같은 질문, 다른 답의 비밀 (`slug: sampling`)

- **훅**: "ChatGPT에게 같은 걸 두 번 물으면 답이 다르다. 고장이 아니라 설정이다."
- **위젯**: `w-sampling` (L1+L2 하이브리드) — 실제 모델에서 뽑은 로짓 분포 1세트(L2)를 놓고, temperature·top-p·top-k 슬라이더로 분포가 재가공되는 것을 실시간 관찰(재가공 연산은 순수 JS라 L1). "샘플 뽑기" 버튼 연타로 확률적 선택 체감. **정확성 관점에서 이상적인 위젯**: 실제 데이터 + 실제 수식.
- **아하**: temperature는 창의성 다이얼이 아니라 확률 분포를 뾰족하게/평평하게 만드는 수학적 조작이다.
- **깊이** — dev: temperature 수식(로짓 나누기), top-p 누적 컷의 정확한 정의, greedy의 반복 문제 / research: nucleus sampling 원문(Holtzman 2019)의 "사람 글은 최고 확률 경로가 아니다" 논증
- **출처**: `holtzman2019`(S1), `openai-api-docs`(S2)
- **연결**: "생성이 길어질수록 모델은 앞에서 한 말을 전부 들고 다녀야 한다. 그 '작업 기억'의 정체와 한계는?"

#### 4-2 컨텍스트 윈도우: 모델의 작업 기억 (`slug: context-window`)

- **훅**: "긴 대화 끝에 ChatGPT가 처음 약속을 잊는 이유 — 기억력이 나쁜 게 아니라 책상이 좁은 것이다."
- **위젯**: `w-context-cost` (L1) — 토크나이저 재사용: 문서를 붙여넣으면 토큰 수 + 컨텍스트 점유율 + 어텐션 연산량의 O(n²) 성장 곡선을 함께 표시. 모델 프리셋은 `data/facts/models.json`에서.
- **아하**: 컨텍스트는 공짜 메모리가 아니다. 토큰 수의 제곱으로 비싸지는 자원이다.
- **깊이** — dev: 어텐션 복잡도 유도, 컨텍스트 확장 기법 개요(포지션 보간 등 — 개념만) / research: 긴 컨텍스트에서의 중간 소실 현상(Liu 2023 "Lost in the Middle")
- **출처**: `vaswani2017`(S1), `liu2023`(S1)
- **연결**: "매 토큰마다 파이프라인을 처음부터 다시 돈다고 했다(2-5). 그럼 1000번째 토큰을 만들 때 999개를 전부 다시 계산하나? — 그러기엔 너무 느리다. 여기 트릭이 있다."

#### 4-3 KV 캐시: 첫 토큰이 제일 느린 이유 (`slug: kv-cache`)

- **훅**: "ChatGPT가 답을 시작하기 전 잠깐 머뭇거리다가, 일단 시작하면 술술 나오는 것 — 느낀 적 있는가. 그 머뭇거림에 이름이 있다."
- **위젯**: `w-kv-cache` (L1) — 두 부분: ① 캐시 없음/있음 생성 애니메이션 비교(재계산량이 극적으로 줄어드는 것) ② KV 캐시 메모리 계산기 — 모델 프리셋(층수·헤드·차원) × 시퀀스 길이 슬라이더 → 캐시 크기 GB. 골든 테스트 대상.
- **아하**: prefill(입력 전체를 한 번에 처리 — 느림)과 decode(캐시 덕에 토큰당 한 걸음 — 빠름)는 다른 국면이다. 그리고 캐시는 VRAM을 먹는다 — 파트 5의 복선.
- **깊이** — dev: 캐시 크기 산식 `2 × layers × kv_heads × head_dim × seq_len × bytes`, GQA가 이걸 줄이는 방식 / research: vLLM의 PagedAttention이 캐시 관리 문제를 푼 방식(Kwon 2023) — 6-4 복선
- **출처**: `kwon2023`(S1, vLLM), `ainslie2023`(S1, GQA — research), `pope2022`(S1, 추론 효율 — research)
- **연결**: "생성은 그럴듯하다. 그런데 가끔 그럴듯한 '거짓'이 나온다. 확률 게임의 구조적 결함인가?"

#### 4-4 환각: 그럴듯한 거짓말의 구조 (`slug: hallucination`)

- **훅**: "모델은 '모른다'는 토큰을 뱉을 이유가 없다 — '아는 척'이 확률적으로 더 그럴듯하다면."
- **위젯**: `w-hallucination` (L2) — 사실 질문들에 대한 모델의 토큰별 확신도(로그확률) 시각화: 정답일 때와 오답일 때 확신도가 잘 구분되지 않는 사례 큐레이션. "확률은 진실의 척도가 아니라 그럴듯함의 척도"를 목격시키는 것이 목적.
- **아하**: 환각은 버그가 아니라 다음 토큰 게임의 본질적 부산물이다. 그래서 완전 제거가 아니라 완화(근거 제공=RAG, 정렬, 검증)로 접근한다.
- **깊이** — dev: 없음(이 챕터는 개념 챕터 — depthLevels에서 dev 생략 허용) / research: 환각 서베이(Ji 2023) 분류, 캘리브레이션 연구 개요
- **출처**: `ji2023`(S1, 서베이), `kadavath2022`(S1, 모델의 자기인식 — research)
- **연결(=파트 연결)**: "능력도 한계도 봤다. 이제 현실적인 질문 — 이 물건은 대체 왜 이렇게 크고, 나는 내 컴퓨터에서 돌릴 수 있는가?"

### 파트 5 — 경량화와 하드웨어 (4챕터) 【실전 — C类 실측 주장 다수, S1 예외 일부 허용】

#### 5-1 파라미터와 VRAM: 모델의 몸무게 (`slug: vram`)

- **훅**: "'7B 모델' — 이 숫자 하나로 당신 GPU에 올라갈지 3초 만에 계산할 수 있다."
- **위젯**: `w-vram-calc` (L1) — **이 사이트의 대표 검색 유입 도구.** 파라미터 수 × 정밀도(FP16/INT8/INT4…) 슬라이더 + KV 캐시(4-3 로직 재사용) + 오버헤드 → 필요 VRAM 막대. GPU 프리셋(3080 10GB, 4090 24GB 등 — facts 파일)과 대비해 "올라감/빠듯/불가" 판정. 골든 테스트 필수.
- **아하**: VRAM = 파라미터 수 × 바이트라는 단순 곱이 출발점이고, 캐시와 오버헤드가 나머지다. 감이 아니라 산수다.
- **깊이** — dev: 학습 시엔 왜 몇 배가 필요한가(그래디언트·옵티마이저 상태) / research: 없음 허용
- **출처**: `transformers-docs-memory`(S2), `data/facts/bench-3080.json`(C类 — 재성 실측)
- **연결**: "14GB가 필요하다는데 내 GPU는 10GB다. 포기? — 아니다. 숫자의 정밀도를 깎으면 된다."

#### 5-2 양자화: 4비트의 마법 (`slug: quantization`)

- **훅**: "소수점 아래를 뭉개서 모델을 4분의 1로 줄였는데 답변 품질은 거의 그대로 — 어떻게 가능하지?"
- **위젯**: `w-quantization` (L1+facts) — ① 수직선 시각화: FP16 값들이 INT4 격자에 스냅되는 것(가중치 히스토그램 → 구간화, 순수 JS) ② 크기·품질 트레이드오프 차트: 공개된 퍼플렉시티 벤치마크(출처 명시, facts 파일)로 "몇 비트까지는 거의 공짜, 그 아래는 급락" 곡선.
- **아하**: 가중치 분포는 대부분 좁은 범위에 몰려 있어 거친 격자로도 근사가 된다. 단, 소수의 아웃라이어가 문제 — 그래서 양자화 '기법'들이 존재한다.
- **깊이** — dev: 양자화 수식(스케일·제로포인트), 그룹 양자화 개념 / research: LLM.int8(Dettmers 2022)의 아웃라이어 발견, GPTQ·AWQ 아이디어 한 단락씩
- **출처**: `dettmers2022`(S1), `frantar2022`(S1, GPTQ), `lin2023`(S1, AWQ)
- **연결**: "이론은 알겠고, 실제로 내려받는 파일들엔 Q4_K_M 같은 암호가 붙어 있다. 해독해 보자."

#### 5-3 GGUF와 로컬 모델 생태계 (`slug: local-models`)

- **훅**: "Q4_K_M, Q5_0, Q8_0… 허깅페이스의 이 암호들, 오늘 해독한다."
- **위젯**: `w-quant-picker` (L1+facts) — 양자화 변형 선택기: 변형별 크기·품질·권장 상황 표(데이터는 facts 파일, llama.cpp 문서 근거) + 5-1 계산기와 연동해 "내 GPU 기준 추천".
- **아하**: 접미사는 비트 수 + 양자화 방식의 조합 표기일 뿐이다. 내 VRAM에서 가장 높은 품질 = 공식 하나로 고른다.
- **깊이** — dev: GGUF 포맷의 위상(llama.cpp 생태계), CPU 오프로딩 개념 / research: 없음 허용
- **출처**: `llamacpp-docs`(S2), `data/facts/bench-3080.json`(C类)
- **연결**: "남의 모델을 돌리는 것까지 왔다. 내 데이터로 '내 모델'을 만들 수는 없을까 — 10GB GPU로?"

#### 5-4 LoRA: 내 GPU로 파인튜닝 (`slug: lora`)

- **훅**: "70억 개 파라미터를 전부 고치는 대신 0.1%짜리 '수정 스티커'만 붙인다면?"
- **위젯**: `w-lora-calc` (L1) — 랭크 r 슬라이더 → 학습 가능 파라미터 수·비율·추가 VRAM 계산 + 어댑터가 원 가중치 옆에 붙는 구조 다이어그램(합성 시각화).
- **아하**: 거대 행렬의 '변화량'은 낮은 랭크로 근사된다는 관찰 하나가, 파인튜닝을 데이터센터에서 책상 위로 가져왔다.
- **깊이** — dev: ΔW = BA 분해 수식, r과 표현력의 트레이드오프 / research: LoRA 원문(Hu 2021)의 가설과 실험, QLoRA(Dettmers 2023)가 5-2와 결합되는 지점
- **출처**: `hu2021`(S1, LoRA), `dettmers2023`(S1, QLoRA)
- **연결(=파트 연결)**: "이제 돌릴 줄도 줄일 줄도 안다. 마지막 파트 — 이걸로 실제로 무언가를 만들자."

### 파트 6 — 활용 (4챕터)

#### 6-1 프롬프트: 확률 게임을 조종하는 법 (`slug: prompting`)

- **훅**: "'단계별로 생각해 보자' 한 줄이 정답률을 몇 배로 올린 사건(2022)이 있다. 마법이 아니라 확률이다."
- **위젯**: `w-prompt-anatomy` (L2) — 같은 과제에 대한 프롬프트 변형(역할 부여, 예시 추가, CoT, 출력 형식 지정)별 실제 출력 비교 갤러리(사전계산·큐레이션). 각 변형이 "다음 토큰 분포를 어느 쪽으로 기울이는가"라는 관점으로 해설.
- **아하**: 프롬프트는 명령이 아니라 조건부 확률의 조건을 설계하는 일이다. 좋은 프롬프트 = 원하는 답이 '그럴듯해지는' 문맥.
- **깊이** — dev: few-shot이 작동하는 이유(인컨텍스트 학습) 개요 / research: CoT 원문(Wei 2022), 인컨텍스트 학습 연구 개요
- **출처**: `wei2022`(S1, CoT), `brown2020`(S1, few-shot)
- **연결**: "프롬프트로 태도는 조종해도 '지식'은 못 넣는다 — 모델이 모르는 우리 회사 문서는? 통째로 붙여넣기엔 컨텍스트가 좁고(4-2), 파인튜닝은 무겁다(3-3). 세 번째 길이 있다."

#### 6-2 RAG: 모델에게 책을 쥐여주다 (`slug: rag`)

- **훅**: "시험 전날 밤새 외우게 할 것인가(파인튜닝), 오픈북 시험을 보게 할 것인가(RAG)."
- **위젯**: `w-rag-sim` (L2, 스트레치 L3) — 미니 RAG 시뮬레이터: 준비된 문서 뭉치 → 청크 분할 → 질문과의 유사도 순위 → 상위 청크가 프롬프트에 삽입되는 전 과정을 단계별로 시각화. 기본은 사전계산 유사도, 스트레치로 transformers.js 소형 임베딩 모델 실검색.
- **아하**: RAG = 1-3 임베딩 지도에서 질문과 가까운 문서 조각을 찾아 4-2 컨텍스트에 실어주는 것. 배운 조각들의 총결합이다. **복선 회수: BERT 계열이 임베딩 모델의 조상으로 여기서 재등장(3-1에서 깐 복선).**
- **깊이** — dev: 청크 크기 트레이드오프, 유사도 검색과 벡터 DB의 위상 / research: RAG 원문(Lewis 2020), 파인튜닝 vs RAG 선택 기준 논의
- **출처**: `lewis2020`(S1, RAG), `karpukhin2020`(S1, DPR — research), `devlin2018`(S1, 재등장)
- **연결**: "검색까지 시켰다. 그럼 계산기도 쥐여주고, 웹도 뒤지게 하고… 모델이 '도구'를 쓰게 하면?"

#### 6-3 에이전트: 도구를 쥔 모델 (`slug: agents`)

- **훅**: "LLM은 계산을 못한다. 그런데 계산기를 '쓸 줄'은 안다 — 이 차이가 에이전트의 전부다."
- **위젯**: `w-agent-loop` (L2) — 스크립트된 시나리오 트레이스 스테퍼: 질문 → 모델의 도구 호출 결정(생각) → 도구 실행 → 결과 관찰 → 재결정 → 최종 답. 각 스텝에서 "이것도 결국 다음 토큰 생성이다"를 강조(도구 호출문 자체가 생성된 토큰).
- **아하**: 에이전트 = 생성 루프에 '행동과 관찰'을 끼워 넣은 것. 새로운 마법이 아니라 프롬프트 설계 + 루프다.
- **깊이** — dev: 도구 호출의 구조(스키마→생성→파싱→실행), 실패 모드(무한 루프, 잘못된 도구 선택) / research: ReAct(Yao 2022), Toolformer(Schick 2023)
- **출처**: `yao2022`(S1, ReAct), `schick2023`(S1, Toolformer)
- **연결**: "마지막 질문. 이 모든 걸 내 컴퓨터에서, 내 서비스에서 돌리려면?"

#### 6-4 로컬 서빙: 내 컴퓨터의 LLM (`slug: serving`)

- **훅**: "인터넷을 끊고도 ChatGPT 비슷한 것과 대화할 수 있다 — 오늘, 당신 컴퓨터에서."
- **위젯**: `w-serving-planner` (L1+facts) — 종합 플래너: 내 GPU 선택 → 5-1·5-3 로직으로 실행 가능 모델·양자화 추천 → ollama 실행 커맨드 생성. 처리량 개념(배치·tokens/s)은 facts의 실측(bench-3080)으로 예시. **커리큘럼 전체의 실전 졸업 과제** 성격.
- **아하**: 파트 5~6의 모든 지식이 "명령어 한 줄"로 수렴한다. 그리고 ollama(개인)와 vLLM(서비스)의 차이는 4-3에서 본 캐시·배치 관리의 차이다.
- **깊이** — dev: 서빙 스택의 층위(모델 파일→추론 엔진→API 서버), 연속 배칭 개념 / research: vLLM 논문 재참조(Kwon 2023)
- **출처**: `kwon2023`(S1), `ollama-docs`(S2), `data/facts/bench-3080.json`(C类)
- **연결**: 완주 축하 + 부록 타임라인·논문 정독 시리즈·도구 모음 안내. (향후 게임 레이어의 진입점이 될 자리 — 지금은 만들지 않음)

구성 4블록 (이 순서대로):
1. **어휘 다리**: "ChatGPT 같은 AI를 LLM(대형 언어 모델)이라고 부릅니다. 이 사이트는 그 속을 열어 보여줍니다" — 사용자 어휘→기술 어휘 번역이 사이트 최초 임무

### 8.2 파일럿 3종 상세 스펙

#### 8.2.1 w-tokenizer

- **목적**: "글 → 토큰 조각"의 목격 + 한국어 비용 체감. 1-1의 앵커이자 `/tools/tokenizer`.
- **UI**: 텍스트 입력(기본 예문 프리셋 칩: 안녕하세요/hello/딸기/사용자 정의) → 아래에 색 블록으로 토큰 렌더(블록 탭 시 토큰 ID·바이트 표시) → 요약 바: 토큰 수·글자 수·글자당 토큰 비율.
- **비교 모드**: 2열 입력(한국어 vs 영어 번역문) → 토큰 수 비율 강조. 인코딩 선택(o200k_base 기본, cl100k_base 옵션).
- **엣지**: 이모지·한글 바이트 폴백(블록이 글자 중간에서 쪼개지는 경우 시각적으로 명확히 — 이게 오히려 교육 포인트), 긴 입력(5,000자 초과 시 절단 안내).
- **테스트**: 대표 문장 10개 토큰 수 스냅샷.

#### 8.2.2 w-next-token

- **목적**: "LLM의 유일한 일"의 목격.
- **UI**: 문장 선택(큐레이션 8~12개: 관용구/사실/애매한 문맥/농담 섞기) → 토큰 단위 스테퍼(◀ ▶) → 각 스텝에서 top-5 후보 확률 막대 + 실제 선택 표시. "내 예상 모드": 다음 토큰을 독자가 먼저 찍고 분포 공개.
- **데이터(L2)**: `scripts/precompute/next_token.py` — 소형 공개 한국어 GPT 모델로 문장별 스텝별 top-k(k=8) 로그확률 추출 → JSON. 모델 선정은 §12(후보: skt/kogpt2-base-v2급 소형 모델). JSON에 모델명·버전·생성일 포함, 위젯 캡션에 노출.
- **스트레치(L3)**: "브라우저에서 직접 돌려보기" 버튼 → transformers.js로 동급 ONNX 모델 로딩(용량 고지 필수). Phase 1에서는 만들지 않는다.
- **주의**: 소형 모델이라 예측이 어설픈 것 자체를 숨기지 말 것 — "작은 모델의 한계"로 정직하게 캡션 처리(3-1 스케일 이야기의 복선이 됨).

#### 8.2.3 w-embedding-map

- **목적**: "의미 = 좌표"의 목격.
- **UI**: 캔버스 산점도(단어 500~1,000개, 시맨틱 줌·팬) + 검색창(단어 하이라이트 + 최근접 이웃 k=10 강조) + 유추 버튼 3~5개(왕−남자+여자 등 — 사전계산 결과만 재생).
- **데이터(L2)**: `scripts/precompute/embedding_map.py` — 공개 한국어 임베딩(후보: FastText 한국어 또는 다국어 문장 임베딩 모델)에서 큐레이션 어휘 추출 → UMAP 2D 투영 → JSON(300KB 예산 내로 어휘 수 조정).
- **정직성 장치**: "이 지도는 수백 차원을 2차원으로 눌러 담은 그림자입니다" 고정 캡션. 유추 결과도 원 공간 기준 계산값을 표시(2D 좌표 연산이 아님을 명시).

### 8.3 사전계산 스크립트 규격 (`scripts/precompute/`)

- Python 3.11+, `uv` 또는 requirements.txt로 환경 고정. **재성의 로컬(RTX 3080)에서 실행**하고 산출 JSON만 커밋한다.
- 모든 스크립트 공통: `--model`, `--seed`, `--out` 인자. 산출 JSON 최상단에 `_meta: { model, revision, script, generatedAt, seed }`.
- 3-1용 체크포인트 캡처: nanoGPT 계열로 소형 한국어 코퍼스 학습(수 시간 내 규모), N개 체크포인트에서 동일 프롬프트 세트 출력 저장. **[재성 액션]** 코퍼스 선정(라이선스 확인 필수)과 실행. 실패 시 폴백: 공개 학습 로그 기반 재구성 + 출처 명시로 챕터는 성립시킨다.
- bench-3080: **[재성 액션]** 실측 기록 — 모델/양자화/컨텍스트/tokens/s/날짜를 JSON에 축적. 실측 없는 조합은 위젯에서 "추정"으로 구분 표기.

- **페이지 하단 고정 요소 순서**: 확인 질문 → 참고문헌 → 검증일 배지 → 다음 챕터 훅 카드.
- **접근성**: 위젯 조작은 키보드 대체 경로 제공, 색만으로 정보 구분 금지(어텐션 세기 = 색+굵기 병행), 모든 시각화에 텍스트 요약 제공.
- 상세 비주얼 톤(로고·컬러)은 Phase 1 중 재성과 별도 세션에서 확정. 그 전까지는 무채색+포인트 1색으로 중립 구현.

## 11. Claude Code 작업 규칙

### 11.1 진행 방식
- Phase·챕터 단위로 작업하고, 각 챕터 완료 시 게이트 통과 현황을 보고한다.
- 재성에게 물어야 할 것: 스펙 충돌, 모델·데이터 선정, 톤 판단, TODO-VERIFY 해소 불가 건. **묻지 말고 진행할 것**: 구현 세부, 리팩토링, 파일 구조 내 정리.
- 커밋 컨벤션: `feat(widget): …` `content(1-1): …` `data(traces): …` `verify(1-1): …`

### 11.2 사실성 규칙 (최우선)
1. 본문·용어사전의 모든 사실 주장은 frontmatter `references`의 S1/S2에 근거해야 한다. 근거를 확인하지 못한 주장은 **쓰지 않거나** `<!-- TODO-VERIFY: 주장 + 필요한 확인 -->`으로 남긴다.
2. 게이트 2(DRAFT)에서 초안을 쓸 때, 해당 챕터의 S1 원문(또는 핵심 섹션)을 먼저 읽고 쓴다. 기억에 의존한 수치·연도·고유명사는 전부 확인 대상이다.
3. 게이트 3(VERIFY)은 반드시 **새 세션**에서, docs/templates/VERIFY.md 프롬프트로 수행한다. 작성 세션에서 자체 검증으로 갈음하지 않는다.
4. 위젯 golden test의 정답값에도 근거 주석을 남긴다. "그럴듯한 값"을 정답으로 넣지 않는다.
5. references.yaml의 URL은 접속 확인 후 기입한다.
6. 단순화는 허용, 거짓이 되는 단순화는 불허 — 경계가 애매하면 dev/research 레이어로 정확한 버전을 병기해 해소한다.

### 11.3 콘텐츠 톤
- 기본 레이어는 P1(비전공 일반인)이 읽는다. 전문용어 최초 등장 시 반드시 `<Term>` 처리 + 한 줄 풀이.
- 문체: 해요체가 아닌 간결한 평서형(합니다체) 기본 — Phase 1 파일럿에서 재성과 확정 후 동결.
- **어휘 다리 규칙(파트 1~2)**: 사용자 어휘(ChatGPT, AI)에서 출발해 기술 어휘로 다리를 놓는다. 기술 어휘(LLM, 모델, 파라미터, 추론 등)는 최초 등장 시 사용자 어휘 번역을 병기하고, 정의(또는 Term 처리) 전 사용을 금지한다. 파트 3부터는 앞서 정의된 어휘를 자유롭게 쓴다.
- 과장 금지("혁명적", "마법" 남용 금지 — 훅에서 제한적으로만), 의인화는 직관 설명 도구로만 쓰고 dev 레이어에서 기계적 실체를 병기.
- 챕터 분량 가이드: 기본 레이어 2,500~4,500자, dev 500~1,500자, research 300~1,000자.

## 13. 확장 로드맵 — 트랙 시스템 (계획만, 착수 금지)

이 사이트의 장기 형태는 "AI를 만지면서 배우는 플랫폼"이며, 트랙 하나 = 재성의 전문성 영역 하나다(LLM 트랙 완성 = LLM 마스터). 지금 하는 것은 대비 3종뿐이다: 트랙 중립 브랜드(D1), frontmatter `track` 필드(§4.1), URL 트랙 프리픽스(§3.4). 용어사전·타임라인·도구는 이미 트랙 공용으로 설계되어 있다.

- **착수 조건**: LLM 트랙 24챕터 완성(Phase 6) + 운영 데이터(검색 유입·완독) 확인 후. 데이터 없이 확장하지 않는다.
- **후보 순서**: ① 딥러닝 기초(LLM 트랙의 3-2 경사하강·1-3 임베딩이 자연 입구 — 크로스링크로 즉시 연결) ② AI 교양(비전공 최상위 깔때기) ③ 클래식 ML(수요 확인 후).
- 트랙 추가 시 이 문서의 §6(커리큘럼)만 트랙별로 신규 작성하면 된다 — §2~5·§11의 시스템은 도메인 무관하게 재사용된다.
